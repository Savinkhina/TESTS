## DWH - собеседование

### Что такое DWH и в чём его ключевое отличие от транзакционной (OLTP) базы данных? Data Warehouse. 
Data Warehouse. Организованное хранилище данных с учетом хранения истории. OLTP (Online Transaction Processing) - транзакционная/оперативная база данных. Её цель — быстро и надёжно обрабатывать много мелких операций в реальном времени.

### Какие основные принципы лежат в основе DWH (Subject-Oriented, Integrated, Nonvolatile, Time-Variant)?
- Subject-Oriented (Предметная ориентация). Данные организованы вокруг бизнес-сущностей и процессов: клиент, продукт, договор, обращение, операция, а не вокруг отдельных прикладных систем. Это упрощает сквозную аналитику.
- Integrated (Интегрированность). Данные из разных источников приводятся к единым определениям, форматам, справочникам и ключам. Например, единый идентификатор клиента и единое определение статуса обращения независимо от CRM или канала.
- Nonvolatile (Неизменяемость). Данные, однажды загруженные в хранилище, как правило, не обновляются и не удаляются, данные не должны произвольно перезаписываться, как в OLTP. Вместо этого новые данные добавляются, формируя архив.
- Time-Variant (Зависимость от времени). Каждая запись в DWH имеет временную метку. Это позволяет анализировать данные с привязкой к конкретному периоду и отслеживать изменения показателей во времени.

### Чем отличается факт от измерения в модели «звезда»?
- Факт - это то, что мы измеряем (числовые показатели). Например транзакции, количество проданных товаров, сумма продажи, выручка, число заказов, время операции
- Измерение — это контекст, в котором это происходит. Договор, клиент, категории, адреса и пр.

### Что такое SCD (Slowly Changing Dimension) и какие типы существуют?
- SCD Type 0 (Неизменяемое измерение). Предполагает, что данные после первоначальной вставки никогда не меняются. Примеры: дата и место рождения, серийный номер устройства, ИНН. 
- SCD Type 1 (Перезапись). При изменении атрибута существующая запись полностью перезаписывается новыми значениями. Историческая информация теряется — в таблице остаётся только текущее состояние. Подходит, когда история не нужна (например, для справочников стран или валют). 
- SCD Type 2 (Добавление новой строки). При каждом изменении создаётся новая версия записи с новым суррогатным ключом. Старая версия помечается как историческая (например, с помощью флага is_current или дат окончания действия valid_to). Этот подход позволяет хранить полную историю изменений. На практике это «золотой стандарт» для аналитических систем. 
- SCD Type 3 (Добавление столбцов для хранения предыдущих значений). Вместо создания новых строк добавляются отдельные столбцы, в которые сохраняются предыдущие значения атрибутов. История ограничена — обычно только одно предыдущее значение. Подходит, когда нужно сравнивать текущее состояние с ближайшей прошлой версией, но не требуется полный журнал изменений. 
- SCD Type 4 (Выделение истории в отдельную таблицу). Текущее состояние хранится в основной таблице измерения, а вся история — в отдельной архивной таблице. Это позволяет разделить нагрузку: быстрая работа с актуальными данными и детальный анализ истории. 
- SCD Type 5 (Комбинированный подход). Гибрид SCD Type 4 и SCD Type 1: история хранится в отдельной таблице, а текущее состояние — в основной (как в Type 1). 
- SCD Type 6 (Гибридный, объединяет элементы SCD Types 1, 2 и 3).

### Типовая архитектура DWH
- Source (источники). Внутренние АС, внешние подключаемые данные (логи, очереди событий)
- Staging (RAW/ODS) (поставка данных). Репликация данных с фиксацией времени загрузки, версии и технические метаданные. Для near-real-time — CDC/Kafka, для batch — ETL/файловые загрузки.
- Core DWH (ядро хранилища). Консолидация из разных источников: приводятся к единым ключам и атрибутам, обогащаются, сохраняется история (единая модель, единая версия правды). Здесь же активно работают с качеством данных. Внутри ядра часто выделяют подслой DDS (Detail Data Store) — оперативное интегрированное хранилище актуальных данных.
- Data Mart Layer (витрины, семантический слой). Здесь данные преобразуют в структуры, удобные для конкретных бизнес-задач и подразделений. Создаются бизнес-сущности в терминах, понятных бизнесу: «клиент», «продажи», «маржинальность». Привязка семантики к физической структуре. Основа для BI и ИИ.
- Потребители. BI-системы, приложения, АС, аналитика и пр.
  
### В чём разница между подходами Инмона («сверху вниз») и Кимбалла («снизу вверх»)?
- Подход Билла Инмона («сверху вниз»). Cначала создаётся централизованное нормализованное хранилище на уровне всего предприятия (Enterprise Data Warehouse, EDW). Данные из разных источников интегрируются, очищаются и приводятся к третьей нормальной форме (3NF), что минимизирует избыточность и обеспечивает целостность. Требует значительных начальных инвестиций в проектирование и долгое внедрение. Нормализованная модель сложнее в разработке, чем денормализованная.
- Подход Ральфа Кимбалла («снизу вверх»). Отправная точка: сначала проектируются отдельные витрины данных под конкретные бизнес-процессы (продажи, маркетинг, финансы). Данные загружаются в промежуточные (staging) области без предварительной очистки. При масштабировании возрастает риск дублирования данных и возникновения несогласованностей между отдельными витринами.
