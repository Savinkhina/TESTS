# ClickHouse 
ClickHouse - это высокопроизводительная колоночная (СУБД), предназначенная для онлайн-аналитической обработки данных (OLAP) и выполнения сложных SQL-запросов в режиме реального времени на петабайтных масштабах. Изначально система была создана в компании Яндекс для задач веб-аналитики сервиса Яндекс Метрика, а в 2016 году исходный код был открыт под лицензией Apache 2.0. Сейчас проект независимо развивает компания ClickHouse Inc.
## Ключевые особенности архитектуры
- **Колоночное хранение данных**: В отличие от традиционных строковых СУБД (таких как PostgreSQL или MySQL), ClickHouse группирует данные на диске по столбцам. Если аналитический запрос агрегирует информацию только из двух столбцов таблицы, система считывает с диска исключительно эти столбцы, полностью игнорируя остальные строки. Это экономит ресурсы ввода-вывода и кратно повышает скорость выполнения запросов.
- **Векторный движок**: Операции выполняются не над отдельными значениями, а над целыми массивами данных (векторами). Это позволяет эффективно использовать возможности современных процессоров (инструкции SIMD).
- **Сжатие данных**: Поскольку в рамках одной колонки находятся однотипные данные, они поддаются эффективному сжатию, что снижает требования к объему дискового пространства.
- **Масштабируемость и надежность**: ClickHouse поддерживает линейное масштабирование и отказоустойчивую репликацию данных.
## Сравнение с транзакционными (строковыми) СУБД
|Критерий|ClickHouse (OLAP)|PostgreSQL / MySQL (OLTP) |
|--------|-----------------|--------------------------|
|**Тип хранения**|По колонкам|По строкам|
|**Основная задача**|	Анализ миллионов строк, агрегации, отчеты|	Быстрое чтение/запись отдельных строк, транзакции|
|**Обновление данных**|	Пакетная вставка большими пачками|	Построчные апдейты, частые точечные изменения|
|**Объем данных**|	Терабайты и петабайты|	До единиц терабайт в рамках одной ноды|
## Первичные ключи в ClickHouse
- Первичные ключи в ClickHouse не уникальны для каждой строки таблицы.
- Первичный ключ таблицы ClickHouse определяет, как сортируются данные при записи на диск.
- Индекс, созданный с помощью первичного ключа, не содержит записи для каждой строки, а вместо этого содержит запись для каждых 8192 строк (так называемый index granularity).
Эта концепция granularity создает разреженный индекс (sparse index), который легко помещается в памяти. Granules (гранулы) представляют собой полосу наименьшего объема данных столбца, который обрабатывается во время запросов SELECT.
### Понимание granules (гранул)
**Гранула** — это наименьший неделимый набор данных, который ClickHouse считывает при поиске по строкам. Это означает, что вместо чтения отдельных строк ClickHouse всегда читает (потоково и параллельно) целую группу (гранулу) строк. Значения столбцов физически не хранятся внутри гранул: гранулы — это просто логическая организация значений столбцов для обработки запросов.
### Параллелизм
- **Уровень 1**. Параллелизм на одном сервере (потоки CPU)
Когда вы отправляете запрос, задействуется пул потоков (Thread Pool). Количество потоков обычно равно количеству ядер вашего процессора (настраивается параметром max_threads).
1. Один общий поиск в RAM: Сначала ClickHouse выполняет бинарный поиск по массиву засечек (индексу). Это происходит в один быстрый поток, так как индекс крошечный и поиск в RAM занимает микросекунды.
2. Нарезка на диапазоны (Ranges): В результате бинарного поиска ClickHouse получает список номеров гранул, которые нужно прочитать. Например, нужно прочитать 100 000 гранул. ClickHouse разбивает этот список на крупные куски — диапазоны гранул (Mark Ranges).
3. Раздача задач ядрам: Если у вас 16-ядерный процессор, ClickHouse создаст 16 потоков. Каждый поток забирает свой диапазон гранул (например, по 6 250 гранул на поток) и работает независимо:
Каждое ядро CPU параллельно выполняет чтение с диска, распаковку блоков и финальный поиск/агрегацию внутри своих гранул.
- **Уровень 2**. Параллелизм на уровне кластера (Шардирование)
Если ваши данные распределены по нескольким физическим серверам (шардам), ClickHouse задействует распределенный параллелизм.
1. Запрос к Distributed-таблице: Вы отправляете запрос на один сервер (сервер-координатор).
2. Веерный запрос: Координатор мгновенно перенаправляет этот SQL-запрос на все шарды кластера одновременно.
3. Независимый бинарный поиск: Каждый сервер параллельно запускает бинарный поиск по своему собственному локальному разреженному индексу в RAM и находит нужные гранулы.
4. Параллельная обработка: Каждый сервер силами своих процессоров (как описано в Уровне 1) обрабатывает свои гранулы.
5. Слияние результатов: Шарды возвращают координатору уже агрегированные, промежуточные «маленькие» результаты, а координатор просто объединяет их и отдает вам.
Как ClickHouse балансирует нагрузку («Умные» потоки). Если один из потоков процессора обработал свой диапазон гранул быстрее других (например, в его гранулах данные лучше сжались или их там физически оказалось меньше), он не простаивает. В ClickHouse реализован механизм **Work Stealing** (кража работы) — свободный поток «крадет» часть необработанных гранул у более загруженного соседа, чтобы запрос завершился максимально быстро.
### Обработка нескольких Primary Index
**Метод 1: Проекции (Projections)** — Самый современный способ
Проекции позволяют автоматически сохранять одни и те же данные на диске в разных физических порядках сортировки.
Когда вы делаете запрос, оптимизатор ClickHouse сам смотрит на секцию WHERE и решает, какую проекцию выгоднее использовать. При этом данные обновляются автоматически и атомарно.
```CREATE TABLE orders
(
    order_id UInt64,
    user_id UInt32,
    order_date Date,
    amount Decimal(10, 2),
    -- Проекция для быстрого поиска по user_id
    PROJECTION alternative_pk_user
    (
        SELECT * ORDER BY user_id
    )
)
ENGINE = MergeTree()
ORDER BY order_id; -- Основной ключ```
- Как это работает: На диске скрытно создаются две копии данных. Если в WHERE указан order_id, используется основной индекс. Если в WHERE указан user_id, ClickHouse использует бинарный поиск по индексу проекции alternative_pk_user.
- Плюс: Всё прозрачно для аналитика, запросы сами становятся быстрее.
- Минус: Требует в два раза больше места на диске при записи.
